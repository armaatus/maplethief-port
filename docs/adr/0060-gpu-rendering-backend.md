# 60. GPU rendering backend: SDL3 GPU behind mt_gfx's draw interface, with offline-compiled HLSL

- **Status:** Accepted
- **Date:** 2026-10-30
- **Issue:** #120
- **Builds on:** [ADR 0039](0039-rendering-backend-software-rasterizer.md) (mt_gfx, the draw interface, the internal scale and the replacement hook), [ADR 0041](0041-texture-formats-and-premultiplied-alpha.md) (guard band, texels as uploaded), [ADR 0042](0042-frontend-game-loop-and-presentation.md) (the present hook, the Presenter), [ADR 0043](0043-scaling-modes-mouse-mapping-and-settings-file.md) (scaling, settings.ini)

## Context

ADR 0039 drew the game's GL ES 1.1 frames with a deterministic software rasterizer and kept the backend swappable behind `maplethief/gfx.h`: every `glDrawArrays` becomes one self-contained `mt_gfx_draw`. M10 renders at N× internal resolution (#88's filters, HD textures). The software rasterizer's cost grows with pixels: at 4× (1920 × 1280) a busy frame shades 16× the pixels of 1×. Issue #120 asks for a GPU backend behind the same interface that renders identically within a documented tolerance at 1× and at 4× in under 2 ms of GPU time per frame on the Mac, selectable in config, with no change above `gfx.h`.

Constraints:

- CI and the Linux container have no GPU. The software rasterizer stays the default and the reference, and its goldens stay exact. GPU comparisons are local tests that skip without a GPU.
- SDL3 is already a static dependency ([ADR 0003](0003-dependencies.md)). SDL's GPU API runs on Metal, D3D12 and Vulkan, and takes shaders as MSL, DXIL or SPIR-V, chosen per device.
- Everything above mt_gfx wants the frame as pixels: the compositor draws UIKit's views on the CPU over the GL slot, and `--shot-gl`/`--capture` write PNGs. The game never reads its own pixels (there is no `glReadPixels`).
- The guest draws on one thread. Frames are small: frame 1 of the boot has 33 draws, a busy map frame a few hundred quads.

## Options considered

1. **The GPU API**
   1. **SDL3 GPU.** One API, one implementation for Metal, D3D12 and Vulkan; already linked. SDL's GPU renderer (`SDL_CreateGPURenderer`) can share the device with the window and runs custom fragment shaders (`SDL_GPURenderState`), which gives the present stage a place for filters. Chosen.
   2. Per-platform Metal/D3D/Vulkan. Three backends to write and keep in step. Rejected.
   3. OpenGL 3.3. Deprecated on Apple. Rejected (as in ADR 0039).
2. **The shader build path**
   1. **SDL_shadercross at run time** (HLSL or SPIR-V in, translated per device). A new dependency carrying DXC and SPIRV-Cross into every build and the release kit, and shader compilation on the player's machine. Rejected.
   2. **glslang + spirv-cross + DXC in the CMake build.** Every developer and CI job would need the toolchain (and DXC on macOS is not packaged). Rejected.
   3. **Offline: HLSL sources, compiled by a pinned container into a committed C++ header.** `scripts/build-shaders` runs `tools/mtport/shaderbuild.py` in `tools/containers/shaders/` (pinned Ubuntu digest and package snapshot; DXC from its GitHub release, sha256 checked): DXC → DXIL (SM 6.0) and SPIR-V (Vulkan 1.0), `spirv-val`, `spirv-cross --msl` from that SPIR-V, and a reflection check that the descriptor sets match SDL GPU's layout. The result is `runtime/src/gfx/gpu/shaders_compiled.h`, with each source's SHA-256 and the tool versions. The build needs no toolchain; CTest `shaders.stamps` (`shaderbuild.py check`) fails when a source no longer matches its stamp. Chosen. These blobs are compiled from our own HLSL, not derived from the IPA, so they may be committed; like any generated file they go in their own commit.
3. **Presentation**
   1. **Read back each frame.** The GPU backend renders the GL target on the GPU, `mt_gfx_target_cpixels` reads it back (a download pass and a fence), and everything above mt_gfx (compositor, `--shot-gl`, the Presenter's upload) works as before. Simple and keeps the seam exact. Chosen for now.
   2. Keep the frame on the GPU and composite UIKit's views as an overlay texture. Saves the read-back and the re-upload (about 10 MB a frame at 4×), but changes the compositor and the frontend. Left to a follow-up (#130).

## Decision

- **The seam.** mt_gfx has a backend slot (`runtime/src/gfx/gfx_internal.h`: `class Backend` with `submit`, `access`, `forget`, `texture_changing`, `end_frame`). With no backend installed (the default) every path is the software rasterizer, unchanged. `mt_gfx_submit` validates the draw as before, then hands it to the installed backend. The functions that hand out a target's pixels sync first: `mt_gfx_target_cpixels` reads the GPU's result back, `mt_gfx_target_pixels` reads back and marks the CPU's copy newer (uploaded before the next draw), `mt_gfx_target_fill` overwrites without a read-back. A texture upload, emptying or destroy first flushes queued draws that use the texture; each texture image has a generation, uploaded to the GPU when a draw first needs it. Replacement images (the hook's k× images) are what goes to the GPU. Installing or uninstalling a backend reads every target back first, so a switch mid-frame keeps the pixels. `gfx.h` gains only `mt_gfx_backend_name()` and documentation; the GLES layer, EAGL, the compositor and the frontend's Screen do not change.
- **The GPU backend** (`runtime/src/gfx/gpu/gpu_backend.cpp`, public `maplethief/gfx_gpu.h`, static library `maplethief_gfx_gpu`): GL ES 1.1's fixed-function pipeline on SDL3 GPU.
  - Each draw's primitives are expanded to lists on the CPU (strips, fans, loops) and appended to one vertex array per flush: clip-space position, s and t, the constant colour as RGBA8 (28 bytes). The vertex shader maps clip depth −w..w to 0..w so the GPU clips the same volume; the fragment shader is texel × colour (`GL_MODULATE`), with a 1 × 1 white texture when untextured. Blending is fixed-function with the eleven GL ES 1.1 factors one to one. Pipelines are keyed by primitive class (triangles, lines) and blend factors and made on first use. Samplers follow the texture's magnification filter and its minification filter's base filter, and its wrap modes. The viewport is the draw's times the target's scale; the scissor is the viewport cut to the target.
  - **Batching:** consecutive draws with the same target, pipeline, texture, sampler, viewport and scissor are one draw call. A flush is one command buffer: a copy pass (texture and target uploads, the vertex buffer, cycled), render passes (load, store), and a download pass when the CPU wants pixels. Flushes happen at `mt_gfx_end_frame`, at a CPU read, and before a queued texture changes. The busy test frame (a full-screen background and 300 blended sprites) is 2 batches.
  - **Matching the software rasterizer.** The GPU's rules are GL's, but three nudges bring its sampling decisions onto mt_gfx's: vertex positions are snapped to mt_gfx's 1/16-pixel grid in window space (when w > 0 and inside the 16w guard band); line endpoints move by (−1/256, −1/256) pixel, the side of the diamond-exit perturbation mt_gfx applies symbolically; texture coordinates get +1/1024 texel so nearest sampling breaks exact ties as `floor(s × size)` does.
  - **Tolerance.** A GPU frame matches the software rasterizer's when at most **0.5%** of the pixels have a channel off by more than **2**. The GPU's 8-bit blending and filtering round differently (off by 1–2 everywhere is normal); the rest are edge pixels where a coverage or texel decision differs (the perspective scene's far texels; a line's end pixel).
  - **Timing:** `MAPLETHIEF_GFX_GPU_TIMING=1` (or `mt_gfx_gpu_set_timing`) waits for every flush with draws on a fence and adds the time from submit to signal to the stats: an upper bound of the GPU's work, since it also holds queueing (behind the window's own command buffers) and the wake-up. The frontend logs the average and worst flush and the **median frame** at exit; the 2 ms bound is checked on the median, because single frames also wait for the OS to schedule the thread.
- **The frontend.** `settings.ini`'s `gfx_backend = software | gpu` (and `--gfx-backend`) chooses. `gpu` (`platform/src/gfx_backend.{h,cpp}`, `GfxBackendHost`) makes an SDL GPU device for the library's shader formats, installs the backend on it, and gives the window SDL's GPU renderer on the same device. Without a GPU device it logs "gfx: the GPU backend is not available: ..." and is the software path; without a GPU renderer for the window, SDL's default renderer presents and mt_gfx still draws on the GPU. The log names what runs: "gfx: mt_gfx draws with gpu (metal); the window's renderer is gpu". SDL GPU has no device under SDL's dummy video driver (Metal needs a view), so GPU runs need the platform's video driver and open a window; the headless tests stay on the software rasterizer.
- **The present stage.** `PresentPass` makes an `SDL_GPURenderState` from a fragment shader of the library, and `Presenter::set_render_state` draws the screen image through it instead of SDL's own texture shader. `present_copy.frag` is the identity pass and the template: it takes SDL's vertex colour (location 0) and texture coordinates (location 1) and the screen texture at slot 0 of set 2. `MapleThief --gfx-prototype --gfx-backend gpu` presents through it and checks the window against the target exactly.
- **How #88 plugs in.** A filter is a new `runtime/src/gfx/gpu/shaders/<name>.frag.hlsl` with `present_copy`'s interface; extra textures (look-up tables) take slots 1+ of set 2 and uniforms (source and output size) slots of set 3, declared in the shader and in the `SDL_GPURenderStateCreateInfo` that `PresentPass::open` fills (to be extended with sampler bindings and `SDL_SetGPURenderStateFragmentUniforms`). `scripts/build-shaders` compiles it into the library; a setting chooses the pass; the Presenter applies it. It needs `gfx_backend = gpu` (SDL's GPU renderer). CG text at output resolution is the replacement hook's k× images, which the GPU backend already samples at their own resolution.

## Consequences

- **Evidence** (Apple M4, macOS, Metal; `tests/cpp/gfx_gpu_test.cpp`, CTest `gfx_gpu.*`, label `gpu`; local only, skipped in CI and without a device): the committed software goldens drawn on the GPU are within tolerance: `gfx_quad_blend` 0 pixels beyond ±2 (max delta 1), `gfx_blend_factors` 0 (max 2), `gfx_perspective` 78 of 19,200 (0.41%), `gfx_lines` 13 of 6,144 (0.21%). The prototype scene and the busy frame at 4×: 0 beyond ±2. A 2× replacement image: 0 beyond ±2. Every sync point (CPU write and read, texture re-upload and destroy, target destroy, a backend switch mid-frame) is checked. The busy frame at 4× (300 blended sprites over a full-screen background, 1920 × 1280): 2 batches, a median of 0.66 ms GPU time over 60 frames in a Release build (1.42 ms in a Debug build with the machine heavily loaded by parallel builds), under the 2 ms bound.
- **The game's own frames** (`mtport.gpucompare`, CTest `platform.gpu_compare`, labels `real_assets;gpu`, local only): the device golden list's fresh run (title, main menu, the intro's speech box with `GL_LINES`, NPC dialogue, first map, popup) with `--gfx-backend software` and `gpu` (Release build, 59 s of game time, 1,202 frames, 122,173 draws: 237,898 triangles and 3,224 lines). At 1×, all six GL frames and all six composited screens are within tolerance: title and main menu identical, NPC dialogue, first map and popup off by at most 1, the intro's speech box 5 of 153,600 pixels beyond ±2 (0.003%: line ends). At 4× (1920 × 1280), all six GL frames are within tolerance: the intro 32 pixels beyond ±2 (0.001%), the NPC dialogue 5, the rest 0. GPU time per frame: a median of **0.82 ms at 4×** and 0.56 ms at 1× (fence-timed upper bounds, with the window open and the machine loaded by parallel builds; per-flush average 1.06 ms at 4×, worst 9.5 ms). Batching: 17,831 batches for 122,173 draws (15 a frame), 3 pipelines.
- The shader build is reproducible: rebuilding the container and the header gave byte-identical blobs (only the header's comment lines changed). `tests/test_shaderbuild.py` checks the naming, the stamps (CR LF counts as LF, for Windows checkouts), the descriptor-set check and that the committed header matches the committed sources.
- Above `gfx.h` nothing changed; the software rasterizer's goldens and tests are untouched and exact. `mt_gfx_counters.pixels` stays 0 on the GPU.
- New: a shader toolchain container (built only when shaders change), a generated header of about 1,000 lines, and per-draw CPU work for expansion and snapping. Changing a shader means running `scripts/build-shaders` and committing the header separately; `shaders.stamps` catches a forgotten rebuild.
- Not verified here: D3D12 (Windows) and Vulkan. Their shaders pass `spirv-val` and DXC, but have not run; the tolerance may need a second look there (#131).
- Read-back presentation costs a fence wait per frame. If a 4× frame's read-back shows up in frame time, the follow-up keeps the GL frame on the GPU.
- We'd know this was wrong if the tolerance hides real differences (a texel decision visibly off in the game) or if a driver needs per-driver nudges; then the GPU path gets its own goldens per driver.
