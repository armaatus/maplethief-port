# 158. libFuzzer targets: one per parser, generated seeds, a CI smoke and CPU-hour local runs

- **Status:** Accepted (delegated by Joris, 2026-11-13)
- **Date:** 2026-11-13
- **Issue:** [#322](https://github.com/armaatus/maplethief-port/issues/322) (epic [#287](https://github.com/armaatus/maplethief-port/issues/287)); [#323](https://github.com/armaatus/maplethief-port/issues/323) adds its targets the same way
- **Builds on:** [ADR 0154](0154-threat-model-for-player-supplied-files.md) (the parsers to cover), [ADR 0157](0157-asan-and-ubsan-preset-and-ci-job.md) (ASan, UBSan, the `asan` CI job), [ADR 0006](0006-continuous-integration.md) (CI and `scripts/ci-scope`), [ADR 0100](0100-public-repository-and-player-releases.md) (no game file in git)

## Context

ADR 0154 lists the parsers that read files a player can be handed: packs, save exports, the IPA. Their unit tests feed the inputs someone thought of. A coverage-guided fuzzer feeds the ones nobody did, and with ASan and UBSan (ADR 0157) a memory or undefined-behaviour error on any of them stops the run. Four questions needed an answer: which fuzzer and toolchain, where the seed inputs come from without a game file, what CI runs, and how the long runs are made and recorded.

## Options considered

1. **libFuzzer** (clang's `-fsanitize=fuzzer`): in-process, one `LLVMFuzzerTestOneInput` per target, the sanitizers built in, nothing to install beyond clang's runtimes. The Linux job of ADR 0157 already uses clang for this reason. Apple's clang has no libFuzzer runtime.
2. **AFL++**: stronger mutators, but a separate tool to pin and install, and its own build wrappers.
3. **A mutation loop of our own** in the doctest programs: no coverage feedback, so it finds little past the first checks.

For the seeds: committed binary files (the usual way, but opaque in review and easy to fill with a crop of a game file by mistake), or seeds **generated by code** at build time.

## Decision

1. **libFuzzer, Linux, clang.** The option `MAPLETHIEF_FUZZ` (top-level `CMakeLists.txt`) needs clang and `MAPLETHIEF_SANITIZE`, adds `-fsanitize=fuzzer-no-link` to our own code (the coverage counters), and makes `tests/` build only `tests/fuzz/`. The **`linux-fuzz` preset** is `linux-asan` plus the option, at `-O1 -g` (Debug, so asserts stay on, at libFuzzer's usual optimisation): configure, a build preset of the `maplethief_fuzz` target, a test preset of the `fuzz` label and a workflow. On a Mac, `scripts/fuzz` runs in the **pinned Linux container** of `tools/containers/linux/` (`scripts/test-linux`'s image: Ubuntu 26.04 by digest, packages from a dated archive snapshot, `clang` and `libclang-rt-dev` among them), arm64 by default. No Homebrew LLVM: the container is already pinned and is what CI's Linux runs.
2. **One target per parser** (`tests/fuzz/NAME_fuzz.cpp`, built as `fuzz_NAME`), each through the entry point the untrusted bytes reach, with the caller's limits. #322's twelve: `zip`, `ipa`, `ipa_parts` (plist strings, the Mach-O cryptid, entry names), `png`, `texpack`, `border`, `wav`, `mp3`, `flac`, `strings`, `settings`, `bindings`. Where a parser promises a round trip (the zip store, `serialise_settings`, `serialise_bindings`) or an output shape (decoded pixels are width × height × 4), the target checks it and traps: a wrong answer is a finding. Targets that write files (`ipa`, `texpack`) use a scratch folder per process and check that a refused import leaves nothing.
3. **Seeds are generated, never committed as files.** `tests/fuzz/seeds/NAME.py` returns `{file name: bytes}`, built in code or read from the synthetic fixtures under `tests/` (`pngfixtures.py`, the MP3 and FLAC files of `tests/cpp/data/audio/` made by `make_tones.py`). `make_corpus.py` writes them into the build tree; the module may set `MAX_LEN`, the target's input limit. A dictionary `tests/fuzz/NAME.dict` (the format's keywords) is optional. `tests/test_fuzz_targets.py` checks that every target has its harness, its seeds and its CMake line, and that the seeds build.
4. **The CI smoke** is CTest `fuzz.NAME`: 30 s per target (`MAPLETHIEF_FUZZ_SMOKE_SECONDS`) from the seeds into a scratch corpus, four at a time, through `fuzz_run.py smoke`. It is a step of ADR 0157's `asan` job (`linux asan+ubsan`), after the tests: `cmake --workflow --preset linux-fuzz`. A finding fails the step, and its input is in the job's uploaded `build/test-output/`.
5. **Long runs are counted in CPU time.** `scripts/fuzz TARGET...|all --hours H` builds the preset and runs each target in its own process until its process has used H hours of CPU (`fuzz_run.py run` restarts libFuzzer until the children's CPU time adds up, since libFuzzer's `-max_total_time` is wall time and the machine is shared). The corpus grows in `build/fuzz/NAME/corpus/` from run to run, and each run appends its CPU and wall seconds, inputs and exit code to `build/fuzz/NAME/runs.jsonl`: the times a pull request quotes.
6. **LeakSanitizer is on for fuzzing** (`detect_leaks=1` in `fuzz_run.py`), unlike the test presets (ADR 0157, #414): libFuzzer reports memory a single input leaves behind, which a parser must not do; the Objective-C teardown that keeps it off for the tests is not reached.
7. **Every finding becomes a regression test in `tests/cpp/`** (a doctest case with the input's bytes written out), then the fix; the input joins the seeds when it reaches a path they don't. A fuzz target's own bug is fixed in the target.
8. **Not fuzzed here, and why:** a texture pack's file *names* and `ui/` paths come from the directory listing, so the `texpack` target fuzzes the file's bytes behind a valid name; the names have unit tests. The CRC-32 of zip entries is kept on, so the `ipa` target rarely changes an Info.plist or executable inside a zip: `ipa_parts` fuzzes those readers directly.

## Consequences

- Each parser of ADR 0154's first group has a fuzz target and a corpus; a pull request that breaks one of them, or adds a crash any seed reaches within 30 s, fails CI.
- The `asan` job builds the runtime and the frontend a second time, with coverage counters; the step adds about seven minutes.
- #323 adds the structured formats' targets (NIBArchive, binary plist, JSON, saves, the state file) through the same function and README.
- A Mac needs Docker (OrbStack or Docker Desktop) to fuzz; the container's first build takes a few minutes.
- How we'd know this is wrong: a crash from the wild in a parser whose target ran its hours (the seeds or the harness miss a path: widen them), or a smoke that fails on CI's machines and not locally (a time-dependent target).
