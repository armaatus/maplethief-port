# 147. The decompilation track: a rewrite is a hook proved equal, and the script VM goes first

- **Status:** Accepted (delegated by Joris, 2026-11-13)
- **Date:** 2026-11-13
- **Issue:** [#382](https://github.com/armaatus/maplethief-port/issues/382)
- **Builds on:** [ADR 0069](0069-guest-function-hooks.md) (guest function hooks), [ADR 0104](0104-input-replay-and-regression-checkpoints.md) (input replay and the regression digest), [ADR 0090](0090-widescreen.md) (widescreen), [ADR 0014](0014-recompiler-design.md) (the recompiler)

## Context

[ARCHITECTURE.md](../ARCHITECTURE.md#later-optional-decompilation-track) names an optional track: once the game is fully playable through recompilation, hot or interesting engine systems are replaced by hand-written C++ that is verified against the recompiled version. It names `CMMap` rendering, `CHero` physics and the script VM, and promises widescreen and real HD rendering from it. #382 asks whether the track is wanted, which system would go first, and how equivalence is proven. The candidates in the issue are the map renderer (real widescreen without ADR 0090's 568-point cap), the sprite drawing (named as the software rasterizer's hot spot) and the script VM.

The sizes come from the call graph of the Ghidra export (`work/ghidra/functions.json`, measured 2026-11-13): the functions a rewrite replaces, and where it stops.

**The map renderer.** There is no map renderer to replace. The loader bakes every tile layer of a map into one bitmap and one texture at load time (`CMMap +0x78`, [formats/map.md](../formats/map.md)); in the field that texture is drawn as one image at the camera's offset. The draw-side map code is the camera (`CMMap_ClampCamera` `0xC069`, `CMMap_FollowCamera` `0xC175`, `CMMap::ScrollCamera` `0xC225`, the getters `0x5CF6D` / `0x5CF81`) and culling (`0x1F051`, `0x1F2B9`, the object loop `0x5C0AD`). The rest of the field's paint is `CStateGame::Paint` `0x87501`, 24,425 bytes that reach 861 functions (366 KiB) through their callees: the hero, mobs, NPCs, effects, the HUD and every popup. That is the whole game's drawing, not a system with an edge. The 568-point cap is not a limit of this code either: ADR 0090's per-frame view width already widens camera, culling and clip for any width up to the map's. What bounds a wider field is data: each area's backdrop is one fixed 480 × 320 image (stretched by 18 % at 568), and 16 of the 90 maps are under 36 tiles wide ([re/widescreen.md](../re/widescreen.md)).

**The sprite drawing.** Every image the game draws goes through `0x247DD` (`DrawImage(img, x, y, anchor)`, 633 bytes, 16 callers: ten 31-byte wrappers, the scissored part-image draw `0x24B3D` and a few paints), whose only call is the textured-quad blit `Sprite_DrawClipped` `0x7CCD` (939 bytes, one caller). With its surface helpers the blit's closure is 9 functions and 1,453 bytes ([formats/png-dat.md](../formats/png-dat.md)). It is the narrowest seam in the drawing, but it is not a hot spot. On map 7.4 on an Apple M4 a tick costs 0.38 ms of guest code on the software backend and 0.77 ms on the GPU backend, against 11.29 ms in `mt_gfx`, the port's own software rasterizer ([testing/switch-performance.md](../testing/switch-performance.md)). The hot spot is host code that the port already owns (ADR 0039); rewriting guest code cannot move it. HD is also already served without it: render scale, text at the render scale (ADR 0066) and texture packs (ADR 0081).

**The script VM.** The game's C++ port of the Lua 2.4 interpreter ([re/script-vm.md](../re/script-vm.md)) is 70 VM functions and 53 native handlers, 123 named functions and 21,431 bytes (`work/re/names/scriptvm.json`), with the undump at 41 functions. `Lua::execute` `0x9BC11` reaches 420 functions (93,876 bytes) only because the natives call into the quest manager, the hero and the inventory; a rewrite stops at the native boundary, `Lua::callNative` `0x9B37D`. The VM is fully specified (67 opcodes, 24 used, the eight differences from Lua 2.4, the 65 natives) and has an oracle outside the game: the compendium's symbolic walker runs every path of every function of the 307 shipped scripts with zero unknown opcodes (`tests/test_compendium_quests_real.py`). It is cold code (an NPC talk, a portal, a map entry, a mob death), so its speed does not matter. What its rewrite unlocks: a VM that checks what it reads (the guest's `Lua::error` is empty, so a bad operand reads past the stack or an array), a trace of every script step and native call when a quest goes wrong, and the base any later script or quest pack would need, since running player-supplied bytecode on the unchecked guest VM is not an option.

`CHero` physics, the architecture's third example, is the gameplay itself: a rewrite risks exactly what the regression digest guards and unlocks nothing that hooks do not already give (ADR 0069's fixes, the Assists).

## Options considered

1. **Keep the track closed.** Nothing in v1 needs it, and two of the three candidates give nothing. But the method costs little to fix now, the script VM has a real use, and the architecture's promise of widescreen and HD from this track is wrong and should be corrected either way.
2. **Open it for performance.** Rejected: guest code is under a millisecond of a 50 ms tick on the Mac. On the Switch (about 23 times slower) the GPU path fits; what is left there is #279's flags, LTO and compositor, all host work.
3. **Open it with the map renderer first,** for widescreen past 568. Rejected: there is no renderer to replace (tiles are baked at load) and the cap is a property of the art, not the code. A wider field is a question for ADR 0090's mechanism.
4. **Open it with the sprite path first,** for HD sprites. Rejected for now: small and well placed, but nothing needs it that render scale and texture packs do not already do. It stays the second candidate, taken up when a feature needs the draw calls as data on the host (for example sub-pixel sprite placement at render scales above 1).
5. **Open it narrowly, with a fixed method, and the script VM first. Chosen.**

## Decision

- **The track is open after v1, in Backlog.** No rewrite is scheduled before M11's exit; the first issue moves to a numbered milestone when Joris schedules it. Performance is not a reason to rewrite a guest system; a host profile that shows a guest function hot reopens that question with numbers.
- **The seam is a guest function hook (ADR 0069).** A rewritten system is a host handler on the system's entry functions that answers `MT_HOOK_HANDLED`. Its data stays in guest memory in the original layout, so the guest code around it (the natives, save states, the save files) sees what it always saw. Where the rewrite needs the rest of the game, it calls guest functions with `mt_call_guest`, as the hooks do today.
- **A switch per system.** Each rewrite is registered on or off by a developer option, off by default, until its proof below holds; the ADR of that system decides when it becomes the default. The recompiled original always stays in the build, so the switch is also the fallback.
- **Equivalence is proven three ways, all before the switch defaults to on:**
  1. **At the hook (shadow runs).** In a test build, each call to the hooked entry runs the original, records its result registers, every guest memory write and the sequence of calls it makes out of the system (for the VM: the natives with their arguments), restores the guest state as the save states do (#202), runs the rewrite, records the same, and fails on the first difference. Shadow runs cover the replay of ADR 0104 and the `play.*` routes the system appears in.
  2. **Over the corpus.** Every shipped input runs through both: for the VM, every function of all 307 scripts, with natives stubbed by a recorder, compared step for step; the symbolic walker is a third opinion.
  3. **End to end.** `scripts/regress` gives the same digest with the rewrite on and off, and the routes that touch the system give the same per-tick state.
- **The first system is the script VM:** `Lua::execute`, its call and stack machinery and the undump, hooked at their entries; the native handlers stay guest code behind `Lua::callNative`. [#386](https://github.com/armaatus/maplethief-port/issues/386) builds it with the shadow-run harness. The sprite path is the second candidate. The map renderer and `CHero` are not candidates.

## Consequences

- The architecture's promise of widescreen and real HD rendering from rewrites no longer holds: this ADR's line in [ARCHITECTURE.md](../ARCHITECTURE.md) says so and names the method and the first system.
- A wider field than 568 points is ADR 0090's question, not this track's: [#387](https://github.com/armaatus/maplethief-port/issues/387) researches it on the backdrop and the narrow maps.
- The shadow-run harness is a test tool other hooks can use: any `HANDLED` handler (ADR 0069's fixes) can be checked against its original the same way where the two should agree.
- A future script or quest pack (M13) needs its own research and ADR; this one only makes a checked VM possible.
- How we'd know this was wrong: the shadow runs find differences the rewrite cannot remove without copying the original's bugs one by one (then the rewrite is a second copy of the same code with no gain, and the switch stays off), or a profile on a target shows guest code, not `mt_gfx` or the compositor, filling the tick (then performance becomes a reason after all, and the sprite path and the field's paint are measured again).
