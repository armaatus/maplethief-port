# 0122. Compendium site generator

- **Status:** Accepted
- **Date:** 2026-11-06
- **Issue:** #215 (epic #210)

## Context

The compendium (epic #210, ADR 0121) is a static site built from the knowledge base (`build/compendium/kb/`, #213), the images step's files (`build/compendium/site/img/`, #216) and hand-written prose in the repository (`docs/compendium/pages/`). It is built on a machine that has the user's own IPA and is never committed. It is served from a sub-path (`https://armaatus.github.io/maplethief-port/`), must open from `file://` for a local preview, and must work on a phone at 320 px and in light and dark mode.

Nine sections (monsters, items, NPCs and shops, world, quests, walkthrough, skills, mechanics, about the game) are written by separate issues in parallel (#218 to #225, #227), so adding a section must not mean editing a shared list. `compendium check` must prove that the site is complete (every entity has a page or an anchor), that every internal link resolves, and that the files are what a fresh build writes.

The repository's viewers (ADR 0010, `tools/mtport/htmlpage.py`) are already static pages made with the Python standard library: escaped text, a sortable and filterable table, deterministic output.

## Options considered

1. **A site tool (MkDocs, Hugo, Jekyll)**: themes, search and navigation come ready. But each is a new dependency (Python packages or a Go binary) to pin on every OS, their output carries versions and timestamps unless configured away, their Markdown flavours accept raw HTML, and the knowledge-base pages would still need a generator of ours that writes Markdown for them to render. Two layers for one site.
2. **Standard-library Python like the viewers**: no new dependency, deterministic by construction, the pages built directly from the knowledge base, the existing table code reused. We write the shell, the search and a small Markdown reader ourselves.
3. **A JavaScript single-page app over JSON**: one page, the data loaded at run time. Needs a web server for `fetch` (not `file://`), gives search engines nothing to index and needs JavaScript for every page.

## Decision

The generator is standard-library Python in `tools/mtport/compendium/`: `site.py` (the `build` and `check` commands and the shell), `siteapi.py` (the page API), `templates.py`, `prose.py`, `defaults.py`, `assets.py` and the plugin package `sections/`.

- **Output.** `python3 -m mtport.compendium.site build` writes `build/compendium/site/`: one HTML file per page, `site.css`, `site.js` and `search-index.js`. Every link is relative and names a file (`monsters/index.html`, never a directory or a path starting with `/`). The directory holds a `.mtport-compendium-site` marker; a build replaces everything in it except `img/`, which belongs to the images step, and refuses a non-empty directory without the marker. Files are written in sorted order, JSON with sorted keys, nothing dated: two builds are byte-identical.
- **Shared CSS and script files** instead of the viewers' inline ones: the site has around a thousand pages, and one cached copy is smaller and still works from `file://`.
- **Sections are plugins.** Each module in `mtport.compendium.sections` exposes `SECTION = Section(id, title, order, kinds, pages, blurb)`, found with `pkgutil.iter_modules`. `pages(ctx)` yields `Page` objects. A plugin whose `id` matches a default section replaces it; `defaults.py` has a default section and page builder for every knowledge-base kind, so the site is complete before any plugin exists, and a kind no section claims goes to an "Other" section. Shop listings, levels, warps and trades are anchored rows of their section's table rather than pages of their own.
- **Link markers.** A builder never computes a URL: `ctx.ref(kind, id)`, `ctx.href(kind, id)` and `ctx.url(path)` return markers, resolved after every page is known to a path relative to the page holding them. A page claims the entities it documents with `page.documents(kind, id, anchor)`; a whole-page claim wins over an anchor, two whole-page claims are an error, and a link to an entity no page documents is a build error.
- **Game text** (names, descriptions, dialogue) is put in an element with `data-verbatim` (`siteapi.verbatim`, `ctx.name`), including the `<title>` of an entity page. The prose lint (#212) skips those elements; `check` runs it on every page when `mtport.prose_lint` is present.
- **Prose** is a small Markdown subset (headings, paragraphs, one-level lists, block quotes, pipe tables, bold, emphasis, code, links to site paths, same-page anchors and `https://` URLs) plus entity references `{{kind:id}}` and `{{kind:id|label}}`. The first line's `# ` heading is the page title. Raw HTML, an unknown reference or anything else outside the subset is a build error with the file and line. A builder uses a prose file with `ctx.prose(path)`; a prose file nobody used becomes a page of its own at the same path and is listed under "Articles" on its section's index. So no game text is ever committed: prose names things only through references.
- **Search** is a JSON list (English name, Korean name, aliases, kind, URL) of every documented entity and every other page, written as `search-index.js` (`window.MTSEARCH = [...]`) so that a `<script>` element loads it from `file://`, where `fetch` of a JSON file is refused. The header's search box loads it on first focus and lists exact, then prefix, then substring matches after NFKC case folding, with the keyboard (up and down, Enter, Escape) and the ARIA combobox pattern; `search.html?q=` lists every match. `site.search` is the same function in Python for the tests.
- **Shell.** A skip link, a header with the site name and search, the section navigation, breadcrumbs (Home, the section, the page), `<main>` and a footer with ADR 0121's disclaimer (one constant, `site.DISCLAIMER`), its "About this site" link to `docs/legal.md#the-compendium-site` and a link to the source.
- **Themes and accessibility.** Colours are CSS custom properties with a dark set under `prefers-color-scheme: dark`; every text colour meets WCAG AA (4.5:1) on every background in both themes, checked by a test from the theme table. Focus is a visible 3 px outline. Every `<img>` has alt text (the manifest's, else the entity's name). The layout is one column below 720 px; wide tables scroll inside their own box, so no page scrolls sideways at 320 px.
- **`check`** builds in memory and reports: every relative `href`, `src` and form `action` resolves to a file of the site (an `img/` file on disk) and every `#fragment` to an element id, no link is absolute, every search entry points at a page (and anchor) that exists, every knowledge-base entity has a page or an anchor (missing ones listed, counts per kind), the prose lint's findings, and every file on disk equals the fresh build.

## Consequences

- No new dependency; the site builds wherever the tests run, and CI tests it on a synthetic knowledge base (`tests/test_compendium_site.py`, `tests/compendiumfixtures.py`), including loading every page and link from `file://` and from a `/maplethief-port/` sub-path under `http.server`, and the site script's search against the Python one under Node when Node is installed.
- We maintain our own Markdown reader. It stays small on purpose: anything it does not know fails the build rather than rendering wrongly.
- Section children (#218 to #225, #227) each add one module and can build in parallel; `check`'s completeness report tells them what is still missing. Page layouts follow the style guide (#212); the defaults are deliberately plain.
- The search index grows with the knowledge base (around 100 bytes per entity) and is loaded only when the search box is used.
- If the site outgrows this (full-text search over prose, many more pages), a client-side full-text index can be added beside `search-index.js` without changing the page API.

## Addendum: the design pass (#230, 2026-11-06)

Joris accepted the standard-library generator on the condition that the site looks like a polished game wiki. The first real build (470 pages) worked but read like a developer tool: 1x sprites, raw knowledge-base fields in the infobox, a dead column beside it, raw drop columns, a plain home page. The stack stays (no dependency, no CDN, no web font, own CSS and a little hand-written script, deterministic output); the shell, the theme and the default builders change.

- **Theme** (`assets.THEMES`): warm paper and plum ink by day, a night-plum page by night, a dusk-plum header band in both themes and one maple-orange accent for marks. Headings use the system serif stack, text the system sans stack. Every text colour meets 4.5:1 on every background, the header's pairs (`assets.PAIRS`) too, and marks that are not text (accent, focus ring, input borders, `assets.MARKS`) 3:1; the contrast test checks all three lists.
- **Shell:** a text logo (the site name beside a four-pointed throwing star drawn for the site; no game or Nexon mark), search in the header band, the section tabs as a strip that scrolls sideways inside the header on a phone (the current tab scrolled into view), the current section marked on its entity pages too. `/` jumps to the search box.
- **Infobox:** the entity's picture scaled up by a whole factor (at most 4) with `image-rendering: pixelated`, from the images step's 2x copy when there is one, a sprite's animation playing unless the reader asks for reduced motion; the Korean name as a subtitle; per kind, the style guide's fields with its labels and units (`Lv. 14`, `20-31 meso (80% of kills)`, `Boss`, `Found on`); bookkeeping fields (`sprite`, `name_fills_field`, file stems, raw table numbers) and fields of unknown meaning left out; the in-game description at the foot. On wide screens it floats right and the sections flow beside and below it (headings and tables avoid the float instead of clearing it).
- **Tables:** readable column names, the linked entry with its icon, numbers right-aligned with thousands separators, units in the cell, the filter box only above tables of more than ten rows. Drop tables show the real odds with the table's own value beside them, `4.03% (40/1000)`, and a tooltip saying why they differ; bookkeeping columns (`slot`, `per`, `nominal_percent`) are gone.
- **Home page:** a short intro, a large search box, the counts per kind and one card per section with a picture.
- **Screenshot check** (`python3 -m mtport.compendium.shots`): serves the built site on localhost and opens a fixed list of pages (the home page, the search page, every section index and one page of each kind) in headless Chrome. A probe page loads each page in an iframe at 320, 390 and 1280 px and reports any page wider than its viewport, with the elements that stick out; then every page is captured in both themes into `build/compendium/shots/`, the phone widths side by side (Chrome's window does not shrink below about 500 px, so a phone width needs a frame of its own). It exits 1 on any sideways scroll and is never part of the deploy. `tests/test_compendium_shots.py` runs it on the synthetic site and on a planted wide element, and skips without Chrome.
- **Page API additions** (backwards compatible): `ctx.sprite(kind, id, box=160, animate=True)` for an entity's picture; `ctx.img(..., scale=n)`; `Images.hires()` and `Images.anim()`; `Section.image` (`"kind:id"` of the home card's picture); `templates.infobox(..., subtitle_markup=, footer_markup=)`, which leaves out rows with an empty value; `templates.Drop(..., per=, percent=)` and `templates.percent_text()`; `templates.num_cell(value, unit)` with separators; `templates.table(..., filter=)`; `defaults.infobox_rows()`, `defaults.entity_sections()` and `defaults.map_figure()` for sections that extend the defaults.

## Addendum: responsive layout (#231, 2026-11-06)

After the design pass Joris looked at the real build on a wide screen: the tables stayed shrink-wrapped against the left edge (the shop's stock table used about a third of the content column) and the row icons came in boxes of different sizes, so rows jumped. The fix lives in the shared stylesheet and builders, so every section page gets it.

- **Tables fill their column.** The table's box (`.wrap`) is a block formatting context with no fixed width, so it takes the content column, or the room beside a floated infobox, and the table inside is `width: 100%`. Text columns share the spare width; numeric columns are as narrow as their numbers (`th.num { width: 1% }`, no wrapping, right-aligned). Long tables keep their sticky header inside a box at most 80% of the viewport high. `templates.table(..., compact=True)` keeps a small table at its natural width; the screenshot check leaves it alone.
- **Narrow screens.** A table wider than its column scrolls inside its own box, never the page: a shadow marks each edge with more to show (background layers fixed to the box, covered at the ends by layers that scroll with the content), and a short line above the box says to scroll sideways once the script sees that it overflows. Cells get less padding below 560 px. Stacked cards were considered and left out: the list tables are for comparing numbers across rows, which a card layout breaks.
- **One picture box per row.** Every row of a table with pictures gets the same 40 px box (`defaults.THUMB_BOX`, the stylesheet's `--thumb`), the picture scaled up by the largest whole factor that fits (`defaults.thumb_scale`) and drawn with `image-rendering: pixelated`; a row without a picture gets an empty box (`defaults.EMPTY_THUMB`) when others have one, so names line up.
- **Breakpoints.** The page is at most 88rem wide (1408 px; 32 px gutters from 1440 px). Below 560 px the infobox sits above the text in one column; from 560 to 999 px it sits above the text with the picture beside the facts; from 1000 px it floats right (24rem wide from 1440 px) and the text and tables flow beside it. Galleries wrap and map images shrink with the column.
- **Screenshot check.** `shots.py` now runs at 320, 390, 768, 1024, 1280, 1600 and 1920 px, and from 1024 px up it flags any table narrower than 60% of its room (the width of its block less a float beside it) unless it is compact. It exits 1 on a narrow table as on sideways scroll.
- **Page API additions** (backwards compatible): `templates.table(..., compact=)`; `defaults.thumb(..., placeholder=)`, `defaults.entry_cell(..., placeholder=)`, `defaults.has_thumb()`, `defaults.any_thumb()`, `defaults.thumb_scale()`.

## Addendum: quests and conversations (#223, 2026-11-06)

The quests section (`tools/mtport/compendium/sections/quests.py`) owns every quest page and all dialogue. A conversation in the knowledge base is a tree of nodes whose paths repeat the same lines under many combinations of quest states (7,273 paths over 108 conversations), so a page cannot list paths.

- **Parts** (`sections/_talk.py`). The lines (`regMsgNPC`, `regMsgHero` keys) and menu rows (`regSelList` keys) become a graph: a path's lines follow each other, and its last line leads to the first line of every path of the next node that the answer allows (Accept or Refuse, the chosen row, or the next box) and whose conditions do not contradict its own. A part is a run of lines with no branch inside; each menu row starts one. Each part keeps the conditions that hold on every path to it (per bounded term, the union of the values its alternatives allow), the natives it calls (shown as stage directions in our words), where it leads and what leads to it.
- **Which page a part is on.** The quest its own natives name (`setQuest`, `getReward`...), else the one quest its conditions name (a quest that must be done counts only when nothing else is named), else the quest most parts of its topic belong to by a majority (the key's prefix, as the script's author grouped the lines), else the quest of the parts it leads to or follows when they agree. Quest parts are on the quest page; the rest (greetings, refusals, portal messages) on the conversation's page `quests/dialogue/<id>.html`, which NPC pages link with `ctx.ref("dialogue", id)`.
- **Each key once.** Every text key of every conversation is on exactly one page, on an element with `data-key`: a quest's title and description in its infobox, a line in the one part that holds it, anything else (titles of crafting and trading orders, keys no path shows) under "Other text" of its conversation. A line a second conversation repeats links to the first instead of showing it again. `quests.key_problems()` checks it; the tests run it on the synthetic and the real build.
- **How to complete** is generated from the knowledge base in the second person (giver and map, each requirement with its best source and where it is, the turn-in or the chapter end that closes the quest); a prose file `docs/compendium/pages/quests/<quest id>.md` replaces the steps of one quest.
- **Shared additions:** a few rules in `assets.CSS` for parts, item source lists and the quest chain diagram (our own SVG per chapter, drawn from `quest.requires`).

## Addendum: the walkthrough (#227, 2026-11-06)

The walkthrough section (`tools/mtport/compendium/sections/walkthrough.py`) is generated from the knowledge base, with prose in `docs/compendium/pages/walkthrough/` for what the data cannot say (each part's goal, boss advice, the story spoilers).

- **The story** is every main-story quest, every quest a chapter end needs, every quest a part names (a side quest whose portal gate or reward the story needs), and, repeatedly, their prerequisites and the quests that alone give an item one of them asks for. Its order is a topological order of the prerequisite graph (`quest.requires` relations that hold on every way to start the quest), ties broken by the parts. `order_problems()` checks that every main-story quest is in it and that no quest comes before one it needs; `route_problems()` checks that every conditional portal on the route names a quest the walkthrough has taken by then. The tests run both on the synthetic and the real knowledge base.
- **Parts** are hand-named groups of story quests (`PARTS`, our own titles). A side quest opens in the part of its latest prerequisite, else the first part whose route passes its giver. A quest whose turn-in waits on another (an item a later quest gives, or a gate on the way) is finished after it.
- **The route** is the shortest way over the exits a chapter's scripts give (a `chapterN/` script replaces the `common/` one of the same name) between the maps where each quest is taken, hunted for and turned in. An item a shop of the chapter sells is bought; otherwise the best spawning drop, preferring one of at least 5% a kill. Gated steps name their condition.
- **The level to aim for** is a computed range, not a number the game gives: the level the story's own EXP reaches (rewards, asked kills and the expected kills for asked items), and the level whose base ACC matches the strongest required monster.
- **Endings** are every `chapter_end` event and the fight of the last chapter's last boss (whose closing scenes are listed in `docs/re/qol.md`). Each gets a section on the endings page.
