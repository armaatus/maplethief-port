# 39. Rendering backend: a deterministic software rasterizer behind a draw interface, presented through SDL_Renderer

- **Status:** Accepted; clipping amended by [ADR 0041](0041-texture-formats-and-premultiplied-alpha.md) (x and y clip to a 16w guard band, the viewport bounds the pixels); primitives amended by #121 (lines are drawn, points still are not); a GPU backend behind the same interface by [ADR 0060](0060-gpu-rendering-backend.md) (the software rasterizer stays the default and the reference)
- **Date:** 2026-10-29
- **Issue:** #55
- **Builds on:** [ADR 0003](0003-dependencies.md) (SDL3, static), [ADR 0005](0005-test-harness.md) (golden images), [ADR 0037](0037-uikit-host-classes-nib-and-compositor.md) (the CPU compositor and its GL slot), [ADR 0038](0038-gl-recording-eagl-silent-audio-boot-to-first-frame.md) (decode, state tracker, command and present hooks)

## Context

The game draws with **OpenGL ES 1.1 fixed-function only** ([ANALYSIS.md → Rendering](../ANALYSIS.md#rendering)): 24 core entry points and 7 `GL_OES_framebuffer_object` ones. It uses `glDrawArrays` with client arrays (vertex and texture coordinates; no colour array), one constant colour (`glColor4x`), 2D textures from `glTexImage2D`, `glBlendFunc`, the three matrix stacks and `glViewport`. There is no `glClear`, no depth or stencil buffer, no lighting, no fog, no `glDrawElements`, no `glReadPixels`. The drawable is one 480 × 320 RGBA8 renderbuffer ([ADR 0038](0038-gl-recording-eagl-silent-audio-boot-to-first-frame.md)). Frame 1 of the real boot has 33 draws; a busy map frame is expected to have a few hundred textured quads.

UIKit's views are already drawn **on the CPU** by the compositor ([ADR 0037](0037-uikit-host-classes-nib-and-compositor.md)), which leaves a GL slot that it fills with a given GL frame (full mode) or leaves transparent (overlay mode).

The targets are macOS 13+ (Metal; OpenGL deprecated), Windows 10/11 (D3D11/D3D12/Vulkan/GL), iOS 16+ (Metal; OpenGL ES deprecated) and Linux/Steam Deck (Vulkan/GL). CI and `scripts/local-ci` run headless: the Linux job is an x86_64 container under Rosetta with no GPU, and macOS CI runners have no usable GPU for tests either. M5's exit criterion is pixel comparison against device screenshots within tolerance, and #56 asks for golden tests that pass **in CI**.

## Options considered

1. **SDL3 GPU** (one API onto Metal, D3D12 and Vulkan).
   - Pro: one modern API on every target, SDL is already a dependency.
   - Con: shaders must ship as MSL, SPIR-V and DXIL. That needs a shader toolchain (SDL_shadercross or glslang + spirv-cross + dxc) in the build, or committed bytecode with a script to regenerate it.
   - Con: no GPU in CI or the Linux container, so the golden tests would either not run there or run on a software Vulkan (lavapipe) that differs from Metal and D3D in rounding and filtering. Goldens per driver, or wide tolerances.
   - Con: fixed-function rules (exact `GL_FIXED` conversions, the device's filtering precision) become shader code tuned per backend.
2. **OpenGL 3.3 core / GLES 3, plus a Metal path** for Apple.
   - Pro: GLES1 maps almost one-to-one onto a small GL 3.3 shader.
   - Con: two backends to write and keep in step, since GL is deprecated on macOS and iOS. Same CI problem as option 1 (Mesa llvmpipe is possible on Linux only).
3. **A software rasterizer on the CPU** that executes the fixed-function pipeline into a 480 × 320 RGBA8 target, with the finished frame presented through **SDL_Renderer** (SDL picks Metal, D3D11/D3D12, Vulkan or GL per platform) as one streaming texture, scaled there.
   - Pro: **deterministic**. The same frame gives the same bytes on every OS and CPU, in CI and in the Linux container, so the golden tests are exact (or nearly so) everywhere and a device screenshot is compared against one picture.
   - Pro: one implementation for every platform, no shader toolchain, no new dependency. It matches the compositor, which is already CPU-side and wants the GL frame as pixels.
   - Pro: the cost is small. 480 × 320 is 153,600 pixels; even with 5× overdraw that is under a million blended texels per frame, a few milliseconds of one core at 60 Hz.
   - Con: higher internal resolutions (M10's HD rendering, #88) cost CPU in proportion to pixels. At 2× (960 × 640) it is still cheap; beyond that a GPU backend may be needed.
4. **A GPU backend now plus the software rasterizer as a test reference.** Two implementations before either is needed; the GPU one would not be testable in CI.

## Decision

- **Option 3.** GLES 1.1 runs on our own software rasterizer, `mt_gfx`, in `runtime/src/gfx/` behind `runtime/include/maplethief/gfx.h`. The platform layer presents the finished frame with SDL_Renderer.
- **The seam is a draw interface, not GL.** `mt_gfx` knows nothing about GL's state machine. #56's GLES layer (`runtime/src/gles/`) resolves the GL state at each `glDrawArrays` into one self-contained **draw** (`mt_gfx_draw`): the primitive, the vertices already transformed to clip space (`mt_gfx_vertex`: x, y, z, w and texture coordinates s, t, after the texture matrix), the constant colour (RGBA8), the bound texture's `mt_gfx` handle or 0, the blend enable and factors, and the viewport. Enum values are GL's, so the GLES layer passes the game's arguments through. A later GPU backend implements the same interface; nothing above it changes. The draws are the command list: `mt_gfx_submit` may execute each at once (the software backend does) or batch them until the target is read.
- **Objects.**
  - A **target** (`mt_gfx_target_create(width, height, scale)`) is an RGBA8 image owned by `mt_gfx`, stored top row first (an image, as `tests/golden/golden.h` and the compositor use). GL window coordinates have y up, so `mt_gfx` maps window row y to image row `height − 1 − y`; nothing above it flips anything. A target is never cleared by `mt_gfx`: its contents survive presents (the game has no `glClear` and overdraws everything).
  - A **texture** is an `mt_gfx` handle with level-0 RGBA8 texels converted from the uploaded format, its size, its min/mag filter (`GL_NEAREST`, `GL_LINEAR`; mipmapped min filters fall back to their base level's filter) and its wrap modes (`GL_REPEAT`, `GL_CLAMP_TO_EDGE`). Defaults are GL's (`GL_NEAREST_MIPMAP_LINEAR` / `GL_LINEAR`, `GL_REPEAT`). Uploads read rows with GL's default 4-byte unpack alignment (the game never calls `glPixelStorei`). Each format/type pair is one row-conversion function in a table (`runtime/src/gfx/texture.cpp`); #55 provides RGBA/UNSIGNED_BYTE, #57 adds the others and decides about premultiplied alpha. An empty texture draws as untextured (GL's incomplete texture), an unknown handle makes the draw invalid.
- **Internal resolution (the seam for M10's HD modes).** A target has a **logical size** (what GL and EAGL see: 480 × 320; the tracker's renderbuffer size and every query answer stay logical) and an integer **scale** N from 1 to 8; its pixels are N × the logical size (`mt_gfx_target_width/height` logical, `mt_gfx_target_pixel_width/height` pixels, `mt_gfx_target_scale`). Draws carry no pixel assumptions: their viewport is logical, and `mt_gfx` multiplies it by N when it maps clip space to window coordinates, so snapping, the fill rule and sampling happen at the target's pixel resolution. N = 1 is bit-identical to GL ES's resolution (the goldens are at N = 1). Presentation (#58, #59) takes a target of any N.
- **Texture replacement (the seam for HD textures and mods, M10).** An optional host hook (`mt_gfx_set_replace_hook`) is called at every level-0 upload that has pixels, with the texture's logical size, format and type and a **content hash** of the uploaded bytes: 64-bit FNV-1a (offset basis `0xCBF29CE484222325`, prime `0x100000001B3`) over the texel bytes GL reads, row by row, without the alignment padding (`mt_gfx_upload_hash`; stable across platforms, hand-written, no dependency). The hook may return an RGBA8 image k × the logical size (one integer k from 1 to 8 for both axes); a wrong size is rejected, logged and counted. The texture keeps its logical size for everything above `mt_gfx` (GL queries, the tracker: `mt_gfx_texture_size`), while sampling uses the replacement (`mt_gfx_texture_texels`): texture coordinates are normalised, so the replacement maps onto the same coordinates, and nearest/linear apply at its resolution. No hook is the default and changes nothing. Statistics count replaced textures, replacements and rejections. The mod-pack loader (files, folders, naming by hash) is M10's.
- **Rasterization rules**, to be as close to the device as the tests can show:
  - Clip-space triangles are clipped (Sutherland–Hodgman) against w > 2⁻²⁰ and the view volume −w ≤ x, y, z ≤ w, always interpolating from the inside vertex towards the outside one so that clipped shared edges stay watertight, divided by w and mapped by the (scaled) viewport. Window coordinates are snapped to **1/16 pixel** (28.4 fixed point, y flipped in integers), and coverage is decided with 64-bit integer edge functions at pixel centres (x + ½, y + ½) with the **top-left fill rule** on the image (y down), so shared edges are drawn exactly once. Each row's covered span comes from exact integer divisions of the edge functions. No culling, depth, stencil or scissor; pixels outside the target are dropped. A triangle with a non-finite vertex is dropped.
  - Primitives: `GL_TRIANGLES`, `GL_TRIANGLE_STRIP`, `GL_TRIANGLE_FAN`. Points and lines return `MT_GFX_UNSUPPORTED`, are counted and logged once per primitive type until the game is seen to draw them.
  - **Amendment (#121):** the game draws `GL_LINES` (`FUN_000082ac`), so `GL_LINES`, `GL_LINE_STRIP` and `GL_LINE_LOOP` are drawn: width 1 (the game never calls `glLineWidth`), GL ES 1.1 section 3.4.1's diamond-exit rule exactly, on the same 28.4 endpoints, in 64-bit integers with the (−ε, −ε²) perturbation applied symbolically. An x-major segment has one pixel in each column whose centre lies in its x-range, plus only its start's own diamond beyond. Its end's diamond is never drawn, so the joints of strips and loops on a diamond are drawn once. Segments are clipped against the same planes as triangles, and the viewport bounds the pixels. Colour, texturing (along the segment, perspective-correct) and blending use the triangles' code. `mt_gfx_counters.lines` and the trace line count them. Points remain `MT_GFX_UNSUPPORTED`: the game draws none. Evidence: `gfx.lines: *` checks hand-derived cases and 3,000 random segments against a transcription of the spec, strips and loops, clipping, blending and texturing; the golden is `gfx_lines.png` (tolerance 0). A local 198 s frontend run to the first NPC dialogue drew 20,400 segments (8 a frame, the dialogue box's border among them) with 0 skipped draws and no points.
  - Texture coordinates are interpolated perspective-correctly from the barycentric weights (the exact integer edge functions, in double), in a fixed order; when a triangle's three w are equal (every ortho draw) the interpolation is affine.
  - Filter choice per triangle: the magnification filter when the triangle maps at most one texel to a pixel along x and along y (within 1/1024; GL's c = 0.5 switch-over for `GL_LINEAR` with a `*_MIPMAP_NEAREST` minification filter), the minification filter's base filter otherwise. GL decides per pixel; for the game's ortho draws that is the same. Nearest: `floor(s × size)`. Linear: the four texels around `(s × size − ½)` with 8-bit weights, `(Σ texel × weight + 32768) >> 16`.
  - Fragment: texel **modulated** by the constant colour (GL ES's default `GL_MODULATE`; the game never calls `glTexEnv`), per channel `(a × b + 127) / 255`. Without a texture the fragment is the colour.
  - Blending: all eleven GL ES 1.1 factors (`ZERO`, `ONE`, `SRC_COLOR`, `ONE_MINUS_SRC_COLOR`, `DST_COLOR`, `ONE_MINUS_DST_COLOR`, `SRC_ALPHA`, `ONE_MINUS_SRC_ALPHA`, `DST_ALPHA`, `ONE_MINUS_DST_ALPHA`, `SRC_ALPHA_SATURATE`) as 8-bit values, accepted on either side (the GLES layer rejects what GL rejects), with one rounding per channel: `min(255, (src × f_src + dst × f_dst + 127) / 255)`. The common `SRC_ALPHA / ONE_MINUS_SRC_ALPHA` and `ONE / ONE` pairs have their own loops with the same arithmetic.
- **Determinism is a requirement**, checked by tests. The rasterizer's sources, and the synthetic scenes of its goldens, compile with floating-point contraction off (`maplethief_strict_fp()` in the top-level `CMakeLists.txt`: `-ffp-contract=off`; `/fp:precise` on MSVC, `/clang:-ffp-contract=off` on clang-cl), as the generated code does; no libm function other than `floor` and `isfinite` is used on the way to a pixel. A golden image of the same synthetic scene matches **exactly** on macOS arm64, macOS x86_64 and Linux x86_64.
- **Statistics and trace.** `mt_gfx_get_stats` counts draws, triangles, pixels shaded, unsupported and invalid draws and the time spent in `mt_gfx_submit`, in total and for the current frame; `mt_gfx_end_frame` (the present hook calls it) logs `gfx: frame N: D draws, T triangles, P pixels, U unsupported, X ms` on the `gfx` trace channel (`MAPLETHIEF_TRACE=gfx`, [ADR 0030](0030-runtime-diagnostics.md)).
- **Presentation.** The present hook (#58) takes the renderbuffer's target, hands it to `mt_uikit_composite` in full mode as the GL slot's frame, and the platform uploads the composited image into one SDL streaming texture (`SDL_PIXELFORMAT_ABGR8888`, which is R, G, B, A in memory; blend mode none) and draws it with `SDL_RenderTexture` into the rectangle #59's scaling chooses, with SDL's nearest, linear or pixel-art scale mode. SDL_Renderer's own backend choice (Metal on Apple, D3D on Windows, Vulkan or GL on Linux) is the only GPU code we have.
- **Prototype (#55):** `mt_gfx` as above; `tests/cpp/gfx_test.cpp` with golden images; `MapleThief --gfx-prototype` showing the prototype scene (`platform/src/gfx_prototype.cpp`) in the SDL window, and the CTest `platform.gfx_prototype` reading it back headless.

## Evidence (prototype, #55)

- **Rules** (`tests/cpp/gfx_test.cpp`, CTest `gfx.*`): a pixel-aligned rectangle covers exactly its pixels; centres on an edge belong to top and left edges only, whatever the vertex order; a 40-triangle fan, a jittered 9 × 7 strip mesh and a quad as strip, list and fan cover every pixel exactly once (additive blending would show a 2); a huge triangle fills exactly a sub-viewport; a quad crossing the clip boundary stays watertight; z outside the volume and w ≤ 0 draw nothing; a triangle crossing the eye plane draws only its visible part; NaN vertices are dropped; nearest and bilinear values are checked by hand (`0, 0, 32, 96, 159, 223, 255, 255` for a black-white texel pair stretched 4×), REPEAT and CLAMP_TO_EDGE, magnification versus minification filter by scale; modulation against `(a × b + 127) / 255` over a grid of values; every one of the 121 factor pairs against a reference written from the spec, on four src/dst pairs, plus hand-computed values; perspective-correct s (texel 1 where affine would give texel 2); points and lines counted and logged once; the `gfx` trace line; scale 2 (edges at twice the positions, half-pixel logical edges on pixel boundaries, the scaled viewport, the prototype scene at scale 2 box-filtered down equal to scale 1 within edge pixels); a synthetic 2× texture replacement (hook arguments, FNV-1a value, logical size kept, 1:1 texels, bilinear at the replacement's resolution equal to a plain 4 × 4 upload, decline, no offer without pixels, a wrong size rejected).
- **Golden images**, synthetic, tolerance 0 (`tests/golden/data/`): `gfx_quad_blend.png` (the prototype scene: a checkerboard background, a 64 × 64 sprite at 3× turned by 30°, bilinear, modulated and alpha-blended; the sprite at 1.5× nearest and tinted; a hexagon fan multiplied in with `DST_COLOR / ZERO`; an additive rectangle), `gfx_blend_factors.png` (11 × 11 tiles, every source × destination factor over gradients with alpha), `gfx_perspective.png` (a checkerboard floor in perspective, cut at the near plane, nearest and bilinear). They match exactly on macOS arm64 (Debug and Release), on macOS x86_64 (the universal Release binary under Rosetta) and in the Linux x86_64 container (`scripts/local-ci --release`).
- **On screen:** `MapleThief --gfx-prototype --smoke-frames 120` on this Mac opens the window with SDL's `metal` renderer (cocoa video driver), reads the presented 960 × 640 frame back with `SDL_RenderReadPixels` and finds the five probe pixels (quad centre `#686A85`, both background cells, hexagon, additive rectangle) exactly equal to the `mt_gfx` target; `platform.gfx_prototype` does the same headless with the dummy driver and the software renderer.
- **Speed** (Apple M4, Release): the `gfx.timing` case, a full-screen opaque textured background plus 300 alpha-blended 32 × 32 sprites at 480 × 320 (460,800 pixels, 3× overdraw), takes **1.6–1.9 ms** a frame on arm64 and 5.6 ms as x86_64 under Rosetta; the 5-draw prototype scene (212,436 pixels) takes about 6.8 ms in a Debug build. The first version, without the per-row spans, the power-of-two REPEAT mask, the white-colour shortcut and the two specialised blends, took 6.3 ms on the same benchmark.

## Consequences

- **Testable everywhere.** #56's synthetic goldens (ortho quad, rotated sprite, blend modes), #57's fringe test and #60's game-screen goldens run in CI and in `scripts/local-ci` on every OS with exact tolerances. A difference between platforms is a bug, not driver noise.
- **#56** builds the fixed-function layer (matrix stacks with 16.16 conversion, client arrays captured from guest memory at draw time, enables, colour, blend state, texture binding) on top of the state tracker of ADR 0038 and emits `mt_gfx` draws from the command hook. **#57** adds the texture formats the game uploads (rows in the conversion table; the hash then covers them too). **#58** connects the EAGL renderbuffer to an `mt_gfx` target (at scale 1 in M5) and presents it in the window. **#59** chooses the destination rectangle and scale mode for any target scale. **#60** compares targets with device screenshots.
- **Speed is watched, not assumed.** `mt_gfx` counts pixels shaded per frame and the time it spends; the `gfx` trace channel logs both. If a real map frame takes more than 4 ms on the Mac, the inner loops get specialised further (nearest/opaque spans, incremental texture coordinates) before anything else changes.
- **The plan for a GPU backend.** The CPU rasterizer is M5's renderer and the reference for every golden image. In M10, a GPU backend on **SDL3 GPU** goes behind the same draw interface ([#120](https://github.com/armaatus/maplethief-port/issues/120)): one modulate shader plus blend state, with the GLES 1.1 factors mapping one-to-one onto SDL3 GPU's, for high internal scales, shader filters and mod effects. Its output is compared against the software rasterizer's on the same draws; the internal-resolution and texture-replacement seams above are what it and the mod tooling build on, so nothing above `mt_gfx` changes.
- **How we'd know this was wrong:**
  - **The CPU cost is too high** on a target we care about (the Steam Deck or an older iPhone) at 480 × 320, or at the internal scales of M10. Then the GPU backend of #120 becomes the default there earlier, and the software rasterizer stays as the reference that its output is compared with.
  - **Device screenshots show filtering or rounding we cannot match** with integer rules (#60). Then the rules change here, once, for every platform.
